## 1. 代码审计（按严重度排；取证=已用真实数据验证，推断=仅代码阅读）

### A1.【高·取证】对齐采样三处 off-by-one，P3 之前必须修

根因同一个：**帧号 1 基（frames.jsonl / hud.jsonl 的 i 从 1 起）与 0 基索引混用**。

1. **点击→帧映射偏早 1 帧**（`ocr_hud.py:61`）：`int(e["t"]-start)` 是 0 基秒数，
   直接当帧号用。帧 i 实际拍摄于 start+(i-1)+δ（δ≈0.25s 初始化延迟）。
   实测：局1 抽查 400 次 down，**288 次（72%）取到的"点击前帧"比真正最后一帧早 1 帧**；
   首胜局 337/400（84%）。例：点击偏移 7.33s → 采到 f7（≈6.3s 画面），真正点击前帧是 f8（≈7.3s）。
   → 状态样本最多陈旧 ~2s 而非 <1s，连点场景下 state 可能不是用户点击时看到的 UI。
2. **首尾帧集合写错**（`ocr_hud.py:53`）：`needed={0, N-1, N-2}`。
   0 号帧不存在（ phantom，200142 的 needed=1226/done=1225 差的就是它）；
   **真正的末帧 N 永远不被采样**。实测：局2（232000）N=1058，结算帧 f1058 不在 hud.jsonl
   （当时靠手动全帧 OCR 补救）；223918/224824/200142 的 hud i_max 均=N-1。
   文档声称"首帧+末两帧（结算页）"，实际是"不存在帧+倒数第2+倒数第3"。
3. **场景边界帧取反**（`analyze_session.py:47-55,133` × `ocr_hud.py:67`）：
   diffs/scenes 的 i 是 frames 列表 0 基 enumerate，帧号=i+1；ocr_hud 直接 `needed.add(d["i"])`
   → 采到的是**旧场景最后一帧**而非新场景第一帧（回合横幅/阶段切换的信息在新帧上）。

影响面：当前回合级曲线影响小（回合是平台期，邻帧同值）；**P3 (state,action) 对齐是直接质量损失**，
且结算末帧漏采会丢结局标签。修后 needed 集合变化 → hud.jsonl 需补读少量帧（~0.47s/帧，便宜）。
确切改法（供主代理参考，不代改）：
- 点击映射改用 frames.jsonl 实际时间戳二分找 last(t ≤ click_t)，不要用算术
  （同时消除 δ 初始化延迟与循环抖动漂移；capture.py meta.start 与 t0 之间有 hook/video init 间隔）。
- 首尾集合改 `{1, N-1, N}`。
- diffs/scenes 消费处 +1，或 analyze_session 直接输出帧号 i（推荐后者，单一口径）。

### A2.【中·取证】parse_hud 文档声称的污染过滤未实现

### A3.【中·推断】enemy_total 与盟约配对的 QC 强度不一致

- `parse_hud.py:151-152`：enemy_total 每行覆盖写（last-write-wins），无众数/QC；
  生命有 rest 众数 canonical，分母 b 的 OCR 误读（38→36 类）会静默 overwrite。
  建议：回合内 b 取众数，与 life 同等待遇。
- `parse_hud.py:63-66`：数字→最近盟约名（<45px）。若某盟约名漏读而其数字读到，
  数字会**错配给相邻盟约**（奇迹/灵巧相邻时尤险）。建议：配对距离超阈值或一名多数字时标 ambiguous，
  不静默归属。局1 曲线未发现问题，属预防性。
